# Local collection implementation

The stable API is published at `packages/party-contract/src/index.ts` (dependency-free) and `packages/party-ui/src/index.ts` (React). These exported types define the implemented contract; the Kart Party reference documents are historical background. The dashboard exposes nine games: six party games, Blockwild, Kitchen Rush and Kart Party. All nine games use the shared room runtime. Kart Party, Blockwild and Kitchen Rush support 1–10 players, including a host playing on the same device. The six party games use a watching display and phone controllers. Do not advertise extra modes without implemented rules/views.

From a game's `src/`, import types and drawing validation from `../../../party-contract/src/index`, and UI and React types from `../../../party-ui/src/index`. Export `manifest` from manifest.ts; export `rules` and `default rules` from server.ts; export `client` and `default client` from client.tsx. Manifest is standalone and must not import server.ts. Client modules must never runtime-import server.ts, content banks, or answer keys. Type-only imports are safe.

`GameRules<State, Input, Action, Settings, PublicView, PrivateView>` is defined in the current party-contract exports. `GameClientModule<Input, Action, Settings, PublicView, PrivateView>` defines DisplayView/ControllerView (required), PersonalView (optional combined view for a playing host; phones-only routing is not implemented), SceneView (optional display scene), SettingsView, InstructionsView, ResultsView (optional), prepare and dispose. View props are the context directly, NOT `{ctx}`. Settings props: `{settings, onChange, disabled}`; instructions: `{role}`; results: `{outcome, publicView, playerId, isHost}`. Prepare receives `{role, signal, assetBase}` and returns void/Promise<void>; dispose returns void. DOM-only modules use prepare plus two animation frames. Optional SceneView mounts during preparation and calls onReady after its actual scene is usable; the Three helper waits for shader compilation and a visible frame. It remains mounted through playing and unmounts at results. See [3D readiness](3D-READINESS.md). Games should support `validateSettings({})` for defaults. Use `null` for unused Input and PrivateView. Each action must include a game-owned turn/question ID and reject obsolete turns; transport independently validates roundId.

Shared UI exports: ArcadeButton (native button props plus tone sun/coral/sky/lime/grape/ghost and size sm/md/lg/xl), Panel (native div props), Eyebrow (native paragraph props), Modal ({title,onClose,children,wide?}), StatusNotice ({children,tone?:error|info|success}), TextInput (native input props), ToggleRow ({label,checked,onChange,disabled?}), Countdown ({deadline,serverNowMs}), DrawingPad ({value:Drawing,onChange,disabled?,label?}), DrawingRenderer ({drawing:Drawing,label?,className?}). These are shared implementations, not game-specific forks.

Drawing schema is `Drawing = {strokes: DrawingStroke[]}`, `DrawingStroke = {color:string,width:number,points:{x:number,y:number}[]}`. Coordinates and width are normalized to the square canvas. Shared `parseDrawing(unknown)` validates and returns sanitized drawing: at most 24 strokes, 480 points total, nonempty strokes, finite coordinates [0,1], widths [0.003,0.04], colors exactly `#05071a #ff5748 #28c6e7 #78d955 #b58aff #ffd24a`; coordinates quantized to 3 decimals. Empty drawings are structurally allowed; games decide submission eligibility. Send one completed drawing inside a game-owned action containing turnId; do not stream points. The transport supports a deliberate 32 KiB envelope limit. DrawingPad enforces these limits and DrawingRenderer displays the same schema.

## Implemented transport and ownership

`apps/party-server/src/room-hub.ts` routes the existing create/join/rejoin handshake to independent rooms on one server. It bounds shared rooms to 32 and shared connections to 256, rejects cross-origin browser upgrades, and gives each room a separate autosave directory. Each `room-server.ts` instance owns its in-memory room, random host/seat credentials, six-character code, ten-seat capacity, presence, selection, readiness, preparation, authoritative scheduling, projections, action acknowledgements, and teardown. The single-room factory remains available to tests. `apps/party-server/src/registry.ts` is the server allowlist. Host identity is independent of the watching display role; phones join player seats.

`packages/party-contract/src/protocol.ts` describes the room/public transport types. JSON envelopes use `v:'1.0'` and `type`. A maximum 32 KiB incoming message, 80 messages/second/socket, 32 total sockets, 12 registered displays, 16 client pending actions, 256 unique action IDs/player/round, 20-second pending lifetime, and 2 MiB socket backpressure bound prevent unbounded traffic/queues. Exact duplicated action IDs return the recorded result; changed payloads are rejected. Per-turn IDs remain game-owned. Outgoing payloads are explicit projections checked for finite serializable values. Held input is coalesced/resend at up to 20 Hz and explicitly released with sequence-checked input.release; 1.5 seconds of silence remains a server fallback. Socket replacement clears old holds. Current six games use discrete actions and null held input.

Preparation requires each connected player/display to finish its DOM or scene readiness barrier, with a 20-second timeout returning to the lobby and naming missing screens. The server publishes startAt one second ahead and calls rules.create with that timestamp only when the common start arrives. Gameplay timers cannot run during preparation. A disconnected preparing screen must report readiness again. The six DOM games prepare no heavy scenes; completed browser checks and remaining device gates are recorded below.

`packages/party-client/src/session.ts` owns one WebSocket once hosting or joining begins, reconnect/backoff, sessionStorage credentials, reliable action retries, monotonic room/snapshot guards, and a lowest-RTT clock estimate. Game views never own or close that socket. Round changes settle old pending actions. Public dashboard browsing uses `/api/catalog` and defers the socket until a room action; saved credentials still reconnect immediately. `apps/party-client/src/catalog.ts` defines search/capability metadata; `dashboard.tsx` renders the shared library at home and in the room picker. `apps/party-client/src/main.tsx` owns the picker/lobby shell, module loader, error boundary, host confirmations and audio controls. `round-runtime.tsx` owns round preparation, SceneView, results and scoped cleanup. Late joins and reconnects prepare their selected module before rendering its live view. Client loading imports only `apps/party-client/src/registry.ts`'s explicit lazy allowlist. Vite's import-graph guard fails a build if game server/content files enter any browser chunk.

`packages/party-ui/src/` centralizes the token stylesheet, licensed local fonts, buttons/panels/dialogs, portrait inputs, normalized drawing pad/renderer, countdowns, and notices. Drawing surfaces alone disable browser gestures; forms remain scrollable and selectable. Every decorative CSS animation/transition obeys reduced motion. Dialogs use native modal opening/Escape, explicit Tab/Shift+Tab wrapping, and focus restoration. HoldButton, SteerPad and RotatePrompt support continuous input. Their pointer/keyboard cancellation is shared; the normal six games do not need them.

The host recovers its authority by credential within 120 seconds or the room closes. Seats persist across disconnects; no silent deletion or player truncation. Newly joined phones wait until the next round. Server restarts discard active rooms. In the public hub, validated Blockwild autosaves are private to their room; hosts can restore latest/previous checkpoints with a ready roster in that room, or resume a preserved world from results. Download a world file before closing the room to import it into a later room. Files survive in the save root but expired rooms have no account-based recovery UI. The lower-level single-room recovery contract remains described in the [3D guide](3D-READINESS.md). `PUBLIC_ORIGIN` enables public HTTPS invitation/QR URLs through a Node-compatible WebSocket host. See [public preview operations](PUBLIC-PREVIEW.md); there is no account system or persistent identity store.

New opt-in realtime games use FixedStepClock with bounded catch-up and a separate snapshot cadence; legacy games retain their 100 ms scheduling. ResourceScope, FrameMetrics and SnapshotBuffer live in party-runtime; the Three.js adapter lives in party-3d. Scene Lab demonstrates these only in explicit QA builds. See [3D guide](3D-READINESS.md) and [3D QA](../../output/3d-prerequisites/QA.md) for the current changes.

## Host players and Kart integration

Selecting a solo-capable game from the public library creates one room and seats its host. In an existing room, the lobby offers **Play on this device** or **Watch only**. The server handles `room.play` only for the host, in the lobby, for a solo-capable game, within the ten-seat limit. Host/player identity uses the same ID and reconnect credential. Selecting a shared-display-only party game returns the host to watching; phone seats keep their IDs and connection.

`packages/games/kart-party/src` adapts the existing race simulation, renderer, interpolation and audio to GameRules and GameClientModule. Steering uses held state; item presses use acknowledged actions. The shared preparation barrier renders the course before the countdown. The old `/kart-party/` landing route redirects into PartyPlay; all platform play uses `/ws`.

The round shell mounts a scene for a playing host and selects a game's PersonalView when supplied. Kitchen Rush combines its kitchen and controls in PersonalView and scales solo star targets/ticket patience. Results receive host authority so campaign progress also saves for a host with a player seat. Blockwild uses its existing first-person controller scene and world-save hooks. Sound defaults on, remembers mute in browser storage and unlocks after browser interaction.

## My Library and curated Discover (2026-09-10)

The default public route is now My Library, empty until the user adds games. `/?view=discover` browses curator-defined sources; details remain at `/?game=id` and `/games/id`. Membership is stored in `party.library.v1` as validated game metadata, separately from old favorites/history. Removing membership does not touch game saves. Removed catalog entries remain visible in the library as unavailable.

`catalog/sources.json` is the source of public discovery metadata. `/api/catalog` reads and validates it per request and returns `sources` alongside the original runtime `games` manifests. `PARTY_CATALOG_PATH` selects a different file. No site rebuild is needed for listing edits; clients refresh while visible every 30 seconds, on focus and manually. See [curation instructions](../../catalog/README.md). The JSON schema and validation are in `packages/party-catalog/src/index.ts`; creator artwork and generic fallbacks are rendered by `catalog-art.tsx`.

External listings open their manually configured HTTPS play URL in a separate tab. This is not an automatic URL importer or embedded game runtime. The nine installed games still use the existing registries and shared room; room pickers retain the runtime game catalog. Validation, browser flows, maximum catalog checks and current preview ownership are recorded in [My Library QA](../../output/playwright/my-library/QA.md).
