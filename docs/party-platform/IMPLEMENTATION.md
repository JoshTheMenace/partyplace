# Local collection implementation

The stable API is published at `packages/party-contract/src/index.ts` (dependency-free) and `packages/party-ui/src/index.ts` (React). These exported types define the implemented contract; the Kart Party reference documents are historical background. The dashboard exposes thirteen games: Inkwave, Kart Party, Blockwild, Kitchen Rush, Night Job, Starship Scramble, Phonedig, Hotpot, Ichi, Island Settlers, Sky Clash, Hijinks and Trolley Court. All thirteen use the shared room runtime. Kart Party, Blockwild and Kitchen Rush support 1–10 players, including a host playing on the same device. Hijinks (2026-10) replaces the six earlier party games: it is one registered game (a whole night in one round) hosting a library of minigames behind its own pack contract, with a watching display and portrait phone controllers. Start with `packages/games/hijinks/DESIGN.md`; its minigames register in `src/minis/registry.server.ts`/`registry.client.ts`, not in the platform registries. It uses windowed action history (`perPlayer: 256`, 32 KiB) because a night has many actions, and `tools/qa-driver.ts` drives a live night through a real TV page, one real phone page and socket bots. Do not advertise extra modes without implemented rules/views.

From a game's `src/`, import types and drawing validation from `../../../party-contract/src/index`, and UI and React types from `../../../party-ui/src/index`. Export `manifest` from manifest.ts; export `rules` and `default rules` from server.ts; export `client` and `default client` from client.tsx. Manifest is standalone and must not import server.ts. Client modules must never runtime-import server.ts, content banks, or answer keys. Type-only imports are safe.

`GameRules<State, Input, Action, Settings, PublicView, PrivateView>` is defined in the current party-contract exports. `GameClientModule<Input, Action, Settings, PublicView, PrivateView>` defines DisplayView/ControllerView (required), PersonalView (optional combined view for a playing host; phones-only routing is not implemented), SceneView (optional display scene), SettingsView, InstructionsView, ResultsView (optional), prepare and dispose. View props are the context directly, NOT `{ctx}`. Settings props: `{settings, onChange, disabled}`; instructions: `{role}`; results: `{outcome, publicView, playerId, isHost}`. Prepare receives `{role, signal, assetBase}` and returns void/Promise<void>; dispose returns void. DOM-only modules use prepare plus two animation frames. Optional SceneView mounts during preparation and calls onReady after its actual scene is usable; the Three helper waits for shader compilation and a visible frame. It remains mounted through playing and unmounts at results. See [3D readiness](3D-READINESS.md). Games should support `validateSettings({})` for defaults. Use `null` for unused Input and PrivateView. Each action must include a game-owned turn/question ID and reject obsolete turns; transport independently validates roundId.

Shared UI exports: ArcadeButton (native button props plus tone sun/coral/sky/lime/grape/ghost and size sm/md/lg/xl), Panel (native div props), Eyebrow (native paragraph props), Modal ({title,onClose,children,wide?}), StatusNotice ({children,tone?:error|info|success}), TextInput (native input props), ToggleRow ({label,checked,onChange,disabled?}), Countdown ({deadline,serverNowMs}), DrawingPad ({value:Drawing,onChange,disabled?,label?}), DrawingRenderer ({drawing:Drawing,label?,className?}). These are shared implementations, not game-specific forks.

Drawing schema is `Drawing = {strokes: DrawingStroke[]}`, `DrawingStroke = {color:string,width:number,points:{x:number,y:number}[]}`. Coordinates and width are normalized to the square canvas. Shared `parseDrawing(unknown)` validates and returns sanitized drawing: at most 24 strokes, 480 points total, nonempty strokes, finite coordinates [0,1], widths [0.003,0.04], colors exactly `#05071a #ff5748 #28c6e7 #78d955 #b58aff #ffd24a`; coordinates quantized to 3 decimals. Empty drawings are structurally allowed; games decide submission eligibility. Send one completed drawing inside a game-owned action containing turnId; do not stream points. The transport supports a deliberate 32 KiB envelope limit. DrawingPad enforces these limits and DrawingRenderer displays the same schema.

Kart Party was rebuilt from scratch on 2026-09-23. `packages/games/kart-party/src` holds its deterministic simulation (`sim/`, shared by the server and client-side prediction), courses, network presentation, renderer and UI; `DESIGN.md` there is the design and module map, and its tests live in `packages/games/kart-party/tests`. The platform's static file helper moved to `apps/party-server/src/static-response.ts`. All games use `/ws`; the `/kart-party/` landing URL redirects into PartyPlay. Switching games keeps the same room code and phone seats.

## Implemented transport and ownership

`apps/party-server/src/app.ts` builds the HTTP and WebSocket application once for two entries: `main.ts` (hosted; unchanged environment contract `PORT`, `PARTY_ASSET_ROOT`, `PARTY_SAVE_ROOT`, `PUBLIC_ORIGIN`, `PARTY_QA`) and `local-host.ts` (packaged consumer host: durable data directory outside any checkout, single-instance reuse through `instance.json` verified by a random instance id, a bounded `startup.lock`, free-port fallback from 4350, system browser launch, and `POST /api/local/stop` accepted only from loopback with a loopback Host and either a same-origin loopback Origin or the recorded bearer stop token; nothing ever signals a PID). `/api/health` and `/api/addresses` carry `host: 'hosted' | 'local'`; the client uses it only to show local-host status and the stop control in Connection help. `npm run build` emits `server.mjs` (hosted, `ws` external) and `local-host.mjs` (self-contained). Packaging and limits: [LOCAL-HOST.md](../LOCAL-HOST.md).

`apps/party-server/src/room-hub.ts` routes the existing create/join/rejoin handshake to independent rooms on one server. It bounds shared rooms to 32, shared connections to 1024 and upgrades to 304 a minute per address, rejects cross-origin browser upgrades, and gives each room a separate autosave directory. Each `room-server.ts` instance owns its in-memory room, random host/seat credentials, six-character code, 64-seat capacity (`MAX_ROOM_PLAYERS` in party-contract), presence, selection, readiness, preparation, authoritative scheduling, projections, action acknowledgements, and teardown. The single-room factory remains available to tests. `apps/party-server/src/registry.ts` is the server allowlist. Host identity is independent of the watching display role; phones join player seats.

`packages/party-contract/src/protocol.ts` describes the room/public transport types. JSON envelopes use `v:'1.0'` and `type`. A maximum 32 KiB incoming message, 80 messages/second/socket, 152 sockets per room (two per seat and display), 12 registered displays, 16 client pending actions, 256 unique action IDs/player/round, 20-second pending lifetime, and 2 MiB socket backpressure bound prevent unbounded traffic/queues. Exact duplicated action IDs return the recorded result; changed payloads are rejected. Per-turn IDs remain game-owned. Outgoing payloads are explicit projections checked for finite serializable values. Held input is coalesced/resend at up to 20 Hz and explicitly released with sequence-checked input.release; 1.5 seconds of silence remains a server fallback. Socket replacement clears old holds. Turn-based party games use discrete actions and null held input.

Preparation requires each connected player/display to finish its DOM or scene readiness barrier, with a default 20-second timeout returning to the lobby and naming missing screens. A manifest may set `prepareTimeoutMs` (20–120 seconds); Inkwave allows 60 seconds for its original 3D engine. Optional `rules.validateStart(players, settings)` rejects invalid roster/settings combinations before preparation, such as a one-player Cargo Terminal round. The server publishes startAt one second ahead and calls rules.create with that timestamp only when the common start arrives. Gameplay timers cannot run during preparation. A disconnected preparing screen must report readiness again. DOM games prepare no heavy scenes; completed browser checks and remaining device gates are recorded below.

`packages/party-client/src/session.ts` owns one WebSocket once hosting or joining begins, reconnect/backoff, sessionStorage credentials, reliable action retries, monotonic room/snapshot guards, and a lowest-RTT clock estimate. Game views never own or close that socket. Round changes settle old pending actions. Public dashboard browsing uses `/api/catalog` and defers the socket until a room action; saved credentials still reconnect immediately. `apps/party-client/src/catalog.ts` defines search/capability metadata; `dashboard.tsx` renders the shared library at home and in the room picker. `apps/party-client/src/main.tsx` owns the picker/lobby shell, module loader, error boundary, host confirmations and audio controls. `round-runtime.tsx` owns round preparation, SceneView, results and scoped cleanup. Late joins and reconnects prepare their selected module before rendering its live view. Client loading imports only `apps/party-client/src/registry.ts`'s explicit lazy allowlist. Vite's import-graph guard fails a build if any `server.ts(x)`, `*.server.ts(x)`, `content*.ts(x)` or `bot.ts` under a game's `src/` enters a browser chunk.

`packages/party-ui/src/` centralizes the token stylesheet, licensed local fonts, buttons/panels/dialogs, portrait inputs, normalized drawing pad/renderer, countdowns, and notices. Drawing surfaces alone disable browser gestures; forms remain scrollable and selectable. Every decorative CSS animation/transition obeys reduced motion. Dialogs use native modal opening/Escape, explicit Tab/Shift+Tab wrapping, and focus restoration. HoldButton, SteerPad and RotatePrompt support continuous input. Their pointer/keyboard cancellation is shared; turn-based party games do not need them.

The host recovers its authority by credential within 120 seconds or the room closes. Seats persist across disconnects; no silent deletion or player truncation. Newly joined phones wait until the next round, and so do the people an over-full room leaves out of a round ([Big rooms](#big-rooms-2026-11-21)). Server restarts discard active rooms. In the public hub, validated Blockwild autosaves are private to their room; hosts can restore latest/previous checkpoints with a ready roster in that room, or resume a preserved world from results. Download a world file before closing the room to import it into a later room. Files survive in the save root but expired rooms have no account-based recovery UI. The lower-level single-room recovery contract remains described in the [3D guide](3D-READINESS.md). `PUBLIC_ORIGIN` enables public HTTPS invitation/QR URLs through a Node-compatible WebSocket host. See [public preview operations](PUBLIC-PREVIEW.md); there is no account system or persistent identity store.

New opt-in realtime games use FixedStepClock with bounded catch-up and a separate snapshot cadence; legacy games retain their 100 ms scheduling. ResourceScope, FrameMetrics and SnapshotBuffer live in party-runtime; the Three.js adapter lives in party-3d. Scene Lab demonstrates these only in explicit QA builds. See [3D guide](3D-READINESS.md) and [3D QA](../../output/3d-prerequisites/QA.md) for the current changes.

## Host players and Kart integration

Selecting a solo-capable game from the public library creates one room and seats its host. In an existing room, the lobby offers **Play on this device** or **Watch only**. The server handles `room.play` only for the host, in the lobby, for a solo-capable game, while the game still has a free seat. Host/player identity uses the same ID and reconnect credential. Selecting a shared-display-only party game returns the host to watching; phone seats keep their IDs and connection.

Kart Party implements GameRules and GameClientModule directly. Steering, drift and item presses travel in held state (presses are wrapping counters so short taps survive coalescing); only the honk is an action. Racer and kart picks use `parseLobbyChoice` + `LobbyView`. The local kart is predicted with the same simulation code, and snapshots use a compact wire codec. The shared preparation barrier renders the course before the countdown. The old `/kart-party/` landing route redirects into PartyPlay; all platform play uses `/ws`.

The round shell mounts a scene for a playing host and selects a game's PersonalView when supplied. Kitchen Rush combines its kitchen and controls in PersonalView and scales solo star targets/ticket patience. Results receive host authority so campaign progress also saves for a host with a player seat. Blockwild uses its existing first-person controller scene and world-save hooks. Sound defaults on, remembers mute in browser storage and unlocks after browser interaction.

## My Library and curated Discover (2026-09-10)

The default public route is now My Library, empty until the user adds games. `/?view=discover` browses curator-defined sources; details remain at `/?game=id` and `/games/id`. Membership is stored in `party.library.v1` as validated game metadata, separately from old favorites/history. Removing membership does not touch game saves. Removed catalog entries remain visible in the library as unavailable.

`catalog/sources.json` is the source of public discovery metadata. `/api/catalog` reads and validates it per request and returns `sources` alongside the original runtime `games` manifests. `PARTY_CATALOG_PATH` selects a different file. No site rebuild is needed for listing edits; clients refresh while visible every 30 seconds, on focus and manually. See [curation instructions](../../catalog/README.md). The JSON schema and validation are in `packages/party-catalog/src/index.ts`; creator artwork and generic fallbacks are rendered by `catalog-art.tsx`.

External listings open their manually configured HTTPS play URL in a separate tab. This is not an automatic URL importer or embedded game runtime. The installed games still use the existing registries and shared room; room pickers retain the runtime game catalog. Validation, browser flows, maximum catalog checks and current preview ownership are recorded in [My Library QA](../../output/playwright/my-library/QA.md).

## Optional persistent game audio

`GameClientModule.AudioView` is an optional nonvisual component mounted by the shell while that game module is selected. It receives the room phase, round ID, current-round public snapshot (or null), connection status, host/role and server clock. It remains mounted across lobby, preparation, play and results, so music need not restart when round scenes change. The game owns mute/unlock handling and disposal; unmounting on game/room change releases its mixer. Sky Clash uses this for one host-display music/effects mix and listens to the existing `party-sound` preference event. Other games retain their existing audio paths.

`GameClientModule.allowPortraitController?(view)` optionally permits portrait menus in a landscape game. It receives only the current round’s public view, or null during preparation. Sky Clash enables it for fighter selection and map voting; countdown and combat use the existing landscape gate and release held input when it returns. Other games retain their existing orientation behavior.

Optional `GameRules.parseLobbyChoice(raw, ready)` validates a public per-seat draft (maximum 2 KiB); `ready=true` must reject incomplete choices. Supporting rooms expose a fresh `lobbyId` and optional `RosterPlayer.lobbyChoice`. A controller sends `lobby.choice` with that ID, then `room.ready` with the same ID. Only its own unready seat may edit; round start validates complete choices and passes cloned values through `RoundContext.players[].lobbyChoice`. Same-game lobby settings retain drafts but reset readiness and the lobby ID; replay/game switch clear drafts. Reconnect retains choices.

Optional `GameClientModule.LobbyView` receives the roster, settings and shell-owned choice/ready callbacks, replacing the standard controller Ready screen. Host Start/Settings and room authority stay in the shell. `immersivePhone` opts into a gesture-driven Full screen/Screen tips button and visual-viewport CSS variables; Sky Clash scopes its compact controls to that flag’s shell class. Unsupported fullscreen APIs keep a usable controller. The site ships a web app manifest (`display: standalone`) and Apple touch icon, so iPhone players, whose Safari has no element fullscreen, get Home Screen steps with the room code from Screen tips; the button hides when already running from the Home Screen.

## Big rooms (2026-11-21)

A room seats `MAX_ROOM_PLAYERS` (64), exported from `packages/party-contract/src/index.ts`. The room server's manifest validation and join limit and the client's seat counter all read that constant; a manifest may declare `players.max` up to it. 32 concurrent players is the size that is regularly exercised; 64 is a safety ceiling. Every game keeps its own `players.max`, and raising one is a game change described in the [handbook](AGENT-HANDBOOK.md#big-rosters).

**Bounds.** They are derived next to their constants in `room-server.ts` and `room-hub.ts`. A room keeps 12 registered displays and allows 152 sockets: every seat and display may briefly hold two, the live one and a replaced one that is still closing, because a Wi-Fi blip reconnects a whole room at once. The per-socket limits (80 messages a second, 32 KiB a message, 2 MiB of backlog) do not depend on roster size. The hub keeps 32 rooms, allows 1024 connections (every room at the tested size of 32 sockets, or about thirteen rooms at the ceiling) and 304 upgrades a minute per address, because one address is often a whole venue behind NAT or every user behind a tunnel.

**Seat colours.** The first ten seats keep the original palette. Seats 11 to 64 get generated hues that are distinct strings and readable on the dark shell, but neighbours can look alike, so pair colour with a name or number. A new seat takes the first unused colour.

**Over-full rooms.** A room can hold more people than the selected game seats. Then Ready means "I am in this round": the first `players.max` people to tap Ready fill it (later taps are refused with a clear message), the host may start once at least `players.min` are Ready, and everyone else watches as late joiners do, with no private view and no input. Only the displays and the phones in the round hold the common start. A host with a player seat must be Ready or switch to Watch only first, because the host's screen is the shared display. Rooms that fit their game are unchanged: everyone must be connected and Ready. A world load during a round keeps that round's players; a restore from the lobby uses the Ready players. `GameClientModule.LobbyView` still receives the whole room roster, which can therefore be longer than the game's maximum.

**Shell.** Up to ten people are listed in the rail as before. Above that the rail keeps only the count and the roster becomes a wall of one-line chips under a "Who's here" disclosure in the main column: open in the lobby under the Start bar, collapsed above the picker, and collapsed on phones as before. The ready sentence names up to three people, or two and a count of the rest. A game without a ResultsView gets a multi-column results list above ten rows, and the host's Play again row stays pinned to the bottom of the screen when results are taller than it.

**Cost.** The room view and the shared part of each snapshot are now checked and serialized once per change and reused for every socket; only the private view is built per seat. Measured with `scripts/qa/room-scale.ts` (Crowd Lab at 20 Hz, real sockets, bots in a second process, a heavily loaded development machine, so treat the figures as relative):

| Players | Server CPU per snapshot, before | after | Server process CPU, before | after | Per socket | Whole room |
| --- | --- | --- | --- | --- | --- | --- |
| 10 | 1.7 ms | 1.2 ms | 14–19% of a core | 12–14% | 56 KiB/s | 0.6 MiB/s |
| 32 | 5.9 ms | 2.0 ms | 22% | 14% | 170 KiB/s | 5.5 MiB/s |
| 64 | 19 ms | 4.3 ms | 47–54% | 20–22% | 337 KiB/s | 21 MiB/s |

What remains is traffic, which grows with the square of the roster because every phone receives every player's state: about 270 bytes a player a snapshot here, and Kart Party and Kitchen Rush send more. That is a game's public view to shrink (a compact codec, a `snapshotCache` field for per-player data that does not change every frame, a lower `snapshotHz`); the platform does not compress or filter snapshots.

**Fixtures.** Crowd Lab (`apps/party-server/src/crowd-lab.ts`, `apps/party-client/src/crowd-lab.tsx`) is a 64-seat fixture registered only in QA builds next to Scene Lab. `scripts/qa/room-bots.ts` fills any room with socket bots and `scripts/qa/big-room-shots.mjs` walks the shell with one real display, one real phone and bots; both are described in the handbook.
